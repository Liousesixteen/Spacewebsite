# SpaceData 实习面试项目讲解手册

这份文档不是产品说明书，而是一份面试复习材料。目标是让你能够从业务目标、系统架构、核心实现、工程取舍、问题排查和未来演进六个层面讲清 SpaceData。

> 使用原则：只讲自己真正理解和参与的工作。本文同时标出了已实现能力与待生产化能力，不要把规划包装成已上线功能。

## 1. 一句话介绍

SpaceData 是一个基于 Next.js 和 PostgreSQL 构建的多语言全球航天数据平台，重点解决两个问题：聚合并持续更新全球近期发射计划，以及用结构化数据展示航天产业链中的企业、技术、材料、设备和上下游关系。

## 2. 30 秒面试版本

> 我做的是一个全球航天数据平台 SpaceData。前端和后端都基于 Next.js 14 App Router 与 TypeScript，使用 PostgreSQL 和 Prisma 建模，数据主要从 Launch Library 2、SpaceX API 和 CelesTrak 同步。核心功能是近期发射任务看板，用户可以查看未来 24 小时、7 天、30 天、正在执行、延期和最近完成的任务；另一个重点是航天产业链，按上游、中游、下游组织企业、技术、材料和设备。项目还实现了四语言国际化、登录与权限、收藏评论、管理后台、数据新鲜度监控、同步任务记录和数据库不可用时的缓存降级。我在开发中重点处理了多源数据标准化、幂等同步、前后端数据流和可靠性问题。

## 3. 2 到 3 分钟完整版本

> 这个项目的背景是，航天信息分散在不同机构和数据源中。普通用户很难在一个地方同时看到近期发射时间、任务状态、火箭、发射机构和发射场，产业研究用户也很难把企业、技术和上下游关系串起来。因此我把产品核心收敛为“发射计划中心”和“航天产业链中心”。
>
> 技术上我选择 Next.js 14 App Router 做全栈框架，React 18 和 Tailwind CSS 构建界面，TanStack Query 管理客户端请求、缓存和轮询；后端使用 Next.js Route Handler 提供 REST 风格 API，Prisma 作为 ORM，PostgreSQL/Neon 存储结构化数据。认证使用 NextAuth v5，支持账号密码以及可选的 GitHub、Google OAuth；国际化使用 next-intl，支持简体中文、英语、日语和俄语。
>
> 数据侧不是简单调用第三方接口后直接展示，而是建立了同步层。同步脚本按机构、火箭、发射场、宇航员、航天器、发射任务的依赖顺序执行，把外部状态和国家代码映射成内部统一枚举，使用 externalId 和 upsert 保证重复运行不会制造重复数据，并通过有限并发、请求重试和部分结果返回处理速率限制。每次同步都会记录状态、耗时、增加、更新、跳过和错误数量，关键字段变化还可以形成变更事件。
>
> 发射页不是普通列表，而是先由服务端把数据计算成未来 24 小时、7 天、30 天、进行中、待定、近期完成和需要关注等业务分组，再由前端每分钟刷新。API 返回数据来源和新鲜度；数据库超时后会尝试返回最后一次成功结果，避免页面直接空白。
>
> 工程上我做了类型检查、Prisma 校验、Node 原生测试和生产构建验证。当前它是功能完整的作品集项目，但我也明确知道生产化还缺 Redis 分布式缓存和限流、真正的通知发送器、API Key 路由鉴权、端到端测试、监控平台和支付系统。这些是下一阶段演进方向。

## 4. 项目解决了什么问题

### 4.1 用户问题

- 发射信息分散，时间、状态、火箭、机构、地点和直播入口不在同一页面。
- 发射时间经常变化，用户需要知道数据来源、更新时间和延期情况。
- 不同数据源的国家、状态、机构和实体命名不统一。
- 航天产业链资料大多是文章，缺少可筛选、可关联的结构化视图。
- 国际用户需要不同语言、时间显示方式和本地化实体名称。

### 4.2 产品答案

- 发射任务控制台：下一次发射、近期窗口、执行状态、结果和异常关注。
- 发射档案：列表、表格、日历、筛选、统计、详情、CSV、RSS 和 ICS。
- 航天实体：国家、机构、火箭、航天器和宇航员档案。
- 产业链：上游、中游、下游，以及企业、技术、材料、设备和市场指标。
- 用户系统：登录、收藏、评论、关注规则和通知中心。
- 运营系统：内容管理、用户管理、同步记录和数据健康页面。

### 不要误讲的技术

- `zustand` 存在于依赖中，但当前代码没有实际使用。不要说项目用 Zustand 管理了全局状态。
- Redis、消息队列、Sentry 和支付仍是规划，不是已实现能力。
- Neon 是 PostgreSQL 的托管形态，不是另一种数据库。

## 6. 系统架构

```mermaid
flowchart LR
    U[浏览器用户] --> MW[Next.js Middleware]
    MW --> P[App Router 页面]
    P --> RQ[TanStack Query]
    RQ --> API[Next.js Route Handlers]
    API --> S[lib/api 业务服务]
    S --> ORM[Prisma Client]
    ORM --> DB[(PostgreSQL / Neon)]

    LL2[Launch Library 2] --> SYNC[同步脚本]
    SPX[SpaceX API] --> SYNC
    CT[CelesTrak] --> SYNC
    SYNC --> ORM
    SYNC --> SR[SyncRun / ChangeEvent]

    API --> FC[内存降级缓存]
    CRON[定时任务] --> IA[/api/internal/sync]
    IA --> SYNC
```

### 分层职责

- `app/[locale]`：多语言页面、路由布局、认证页面与管理后台。
- `app/api`：HTTP 边界，负责解析参数、鉴权、调用服务并生成响应。
- `components`：通用 UI 与发射、产业链、用户等业务组件。
- `lib/api`：可复用业务规则，例如发射分组、筛选参数、数据质量和通知判定。
- `lib/db`：Prisma 单例，避免开发热更新时重复建立客户端。
- `scripts/sync`：外部数据抓取、标准化、关联解析和入库。
- `prisma`：数据库模型、迁移和种子数据。
- `messages`：四种语言的翻译字典。
- `tests/api`：纯逻辑与服务辅助函数测试。

## 7. 一次发射页面请求是怎样完成的

这是最值得在面试中讲清楚的一条链路。

1. 用户访问 `/zh-CN/launches`。
2. Middleware 校验语言前缀，并添加 CSP、`X-Content-Type-Options`、Referrer Policy 等安全响应头。
3. 发射页加载后，TanStack Query 请求 `/api/launches/overview` 和 `/api/launches`。
4. 列表 API 解析页码、状态、国家、年份、火箭、机构、轨道和日期范围等参数。
5. Prisma 同时执行 `findMany` 与 `count`，并关联查询 Rocket、Agency、LaunchSite、LaunchPad 和 Payload。
6. 概览 API 查询最近 14 天到未来一年范围内的数据，并设置 10 秒数据库超时。
7. `buildLaunchOverview` 将任务计算成下一次、24 小时、7 天、30 天、进行中、日期待定、最近完成和异常关注分组。
8. API 添加 CDN 缓存语义：`s-maxage=60, stale-while-revalidate=120`。
9. 前端展示本地时间或 UTC，并每 60 秒重新拉取概览。
10. 如果数据库请求失败，API 尝试返回最近一次成功的内存缓存，并通过 `X-Data-Source: fallback` 标记降级来源。

可以用一句话总结：页面只负责交互和展示，Route Handler 负责 HTTP，`lib/api` 负责业务计算，Prisma 负责数据访问。

## 8. 数据模型怎样设计

数据库当前包含 34 个 Prisma 模型，可以按五个领域理解。

### 8.1 航天核心实体

- `Launch`：发射时间、窗口、状态、任务类型、轨道、媒体和来源。
- `Rocket`：制造商、国家、尺寸、运力、级数、首飞和状态。
- `Agency`：机构名称、类型、国家、负责人、官网和外部 ID。
- `LaunchSite` / `LaunchPad`：发射场与具体工位分层建模。
- `Payload`：载荷、所有者、运营者、轨道和 NORAD 标识。
- `Spacecraft` / `Astronaut` / `LaunchCrew`：航天器、宇航员和任务乘组关系。

### 8.2 产业链实体

- `IndustrySegment`：UPSTREAM、MIDSTREAM、DOWNSTREAM 三层产业环节。
- `Company` 与 `CompanySegment`：企业与产业环节多对多关系。
- `Technology`、`Material`、`Equipment`：技术、材料和设备档案。
- `ProductCapability`：企业的具体产品能力。
- `OrganizationRelationship`：供应、合作、投资等组织关系。
- `MarketMetric`：市场规模、增长率等带年份和来源的指标。

### 8.3 用户与内容

- `User`、`Account`、`Session`、`VerificationToken`：NextAuth 相关模型。
- `Favorite`、`Comment`：收藏和评论。
- `Watchlist`、`AlertRule`、`NotificationDelivery`：关注对象、提醒规则和投递记录。

### 8.4 数据治理

- `DataSourceRecord`：外部记录与内部实体的对应关系。
- `SyncRun`：每次同步运行的状态和结果。
- `ChangeEvent`：发射时间或状态等关键字段变更。
- `EntityAlias`：多语言名称和别名解析。
- `FieldEvidence`：字段级来源、置信度和证据。

### 8.5 开发者平台

- `ApiKey`：只保存 Key 哈希、前缀、权限与撤销时间。
- `UsageRecord`：记录 API 使用量，为配额与计费预留。

### 关系数据库为什么合适

这个产品有大量明确关系：一次发射属于一个火箭和发射场，可以属于一个机构和发射台，并拥有多个载荷和乘组；一家企业也可以横跨多个产业环节。这类关联查询、约束和事务比文档数据库更适合 PostgreSQL。

## 9. 多源数据同步怎样实现

### 9.1 数据源

- Launch Library 2：主要的发射、机构、火箭、发射场、宇航员和航天器数据。
- SpaceX API：补充 SpaceX 历史任务、火箭、发射场和直播链接。
- CelesTrak：卫星目录相关数据。
- 项目种子数据：产业链、技术、材料和设备的基础演示数据。

### 9.2 为什么不能直接在前端调用第三方 API

- 数据源字段和状态定义不同，前端会被迫处理大量兼容逻辑。
- 第三方接口有速率限制和故障风险。
- 无法保留历史快照、变更记录和字段来源。
- 用户列表、统计、筛选和关联查询会受上游 API 能力限制。
- API Key 可能泄露给浏览器。

所以项目采用“外部源 -> 同步层 -> 内部统一模型 -> 自有 API -> 前端”的结构。

### 9.3 同步流程

1. 按依赖顺序同步机构、火箭、发射场、宇航员、航天器和发射任务。
2. HTTP 客户端处理分页、请求间隔和三次线性退避重试。
3. 映射国家代码、外部状态、日期和描述字段。
4. 通过 `externalId` 查找已有数据。
5. 缺少依赖实体时先创建占位火箭、机构或发射场，满足外键约束。
6. 使用 `upsert` 或存在性检查实现幂等写入。
7. 使用 `memoizeAsync` 避免同一批次重复解析同一关联实体。
8. 使用 `mapLimit` 将并发限制为固定数量，避免压垮上游或数据库。
9. 将 added、updated、skipped、status 和 error 写入 `SyncRun`。
10. 连续失败达到阈值且配置 Webhook 时发送同步故障告警。

### 9.4 什么是幂等

同一同步任务执行一次和执行多次，最终数据库结果应保持一致。项目用稳定的 `externalId` 和唯一约束识别同一个外部实体，再更新已有行，而不是每次插入新行。

面试官问为什么重要时，可以回答：定时任务可能重试、超时后被再次触发，非幂等逻辑会生成重复发射任务并破坏统计结果。

## 10. 前端如何设计

### 10.1 信息架构

一级导航围绕高频任务收敛：发射计划、航天档案、国家与机构、产业链和通知。时间线、对比等低频能力进入相关详情页，不占用一级入口。

### 10.2 状态划分

- 服务端状态：由 TanStack Query 管理，包括 data、loading、error、cache 和 refetch。
- 页面交互状态：用 React `useState` 管理页码、筛选、视图模式、活动 Tab 和 UTC/本地时间。
- 会话状态：由 NextAuth Session Provider 管理。
- 当前没有使用 Zustand，因为项目尚未出现必须跨大量无关组件共享的复杂客户端状态。

### 10.3 响应式与组件化

- UI 基础组件包括 Button、Card、Badge、StatusBadge、Pagination、Breadcrumbs 和 SmartImage。
- 业务组件按领域组织，如 LaunchMissionControl、LaunchCalendar 和 IndustryChainBrowser。
- 页面支持网格、表格和日历模式，移动端导航单独处理。
- 图标统一使用 Lucide，避免图标尺寸和基线不一致。
- 图片通过 SmartImage 提供加载失败后的领域默认图。

### 10.4 国际化

- URL 始终带语言前缀：`/zh-CN`、`/en`、`/ja`、`/ru`。
- Middleware 负责 locale 路由。
- `messages/*.json` 保存界面文案。
- `display-names.ts` 处理国家、机构、火箭、任务类型等实体名称本地化。
- 日期使用 locale 和时区格式化，发射页可切换本地时间与 UTC。

界面文案翻译和数据实体翻译是两件事。只翻译按钮并不能解决外部英文实体混入中文页面，因此项目另外建立了实体显示名称映射。

## 11. 后端和 API 如何设计

### 11.1 Route Handler

API 位于 `app/api/**/route.ts`，覆盖列表、详情、统计、搜索、产业链、用户行为、管理后台、健康检查、导出、RSS、ICS 和内部同步。

典型职责是：

1. 读取并校验 query/body。
2. 执行用户或管理员鉴权。
3. 调用 Prisma 或 `lib/api` 中的业务函数。
4. 返回稳定 JSON 结构和正确 HTTP 状态码。
5. 对适合缓存的公开 GET 接口添加缓存头。

### 11.2 参数与分页

发射列表支持分页与组合筛选，API 同时返回：

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 486,
    "totalPages": 25
  }
}
```

列表查询和总数查询通过 `Promise.all` 并发执行，避免不必要的串行等待。

### 11.3 导出与订阅

- CSV：供研究用户下载发射记录。
- ICS：将单次发射加入日历。
- RSS：订阅近期发射更新。
- JSON-LD、sitemap 和 robots：支持搜索引擎理解与抓取公开内容。

## 12. 认证、权限和安全

### 12.1 认证

- Credentials 登录从数据库读取用户，并通过 bcrypt 比较密码哈希。
- 注册要求合法邮箱和至少 8 位密码，使用 bcrypt cost 10 哈希后入库。
- OAuth Provider 只有配置对应环境变量时才启用。
- Session 使用 JWT 策略，token 中携带 user id 和 role。

### 12.2 权限

- 普通用户可以管理个人资料、收藏和评论。
- 管理页面通过 `requireAdmin` 做服务端保护。
- 管理 API 通过 `getAdminOrNull` 检查会话和数据库角色。
- 内部同步 API 使用 `Authorization: Bearer <CRON_SECRET>`。

### 12.3 安全措施

- 密码和 API Key 都不以明文形式存储；API Key 设计使用 SHA-256 哈希并只展示前缀。
- Middleware 设置 CSP、禁止 MIME sniffing、禁止 iframe 嵌入和限制浏览器权限。
- API 有每 IP 每分钟 120 次的基础内存限流。
- 同步入口校验 secret，并阻止两小时内同一任务重复运行。
- `.env` 不进入版本控制。

### 12.4 必须主动承认的边界

- Middleware 和 token bucket 都使用进程内 Map，多实例部署时状态不共享，应迁移到 Redis。
- `/api/keys` 当前只完成 Key 生成和权限纯逻辑，路由中的用户鉴权与数据库持久化仍有 TODO，不能称为完整开发者平台。
- CSP 仍允许 `unsafe-inline` 和 `unsafe-eval`，需要结合框架 nonce 进一步收紧。
- 当前 API CORS 使用 `*`，生产环境应设置允许域名列表。

## 13. 可靠性和可观测性

### 已实现

- Prisma 查询错误捕获与结构化错误响应。
- 发射概览查询 10 秒超时。
- HTTP 重试、分页、速率限制下的部分数据返回。
- API CDN 缓存头和 `stale-while-revalidate`。
- 最近一次成功结果的内存降级缓存。
- `SyncRun` 记录任务状态和处理数量。
- `/api/health` 检查应用、数据库和关键表。
- `/api/data-health` 检查各领域数据量、更新时间、新鲜度和最近同步。
- 连续同步失败的 Webhook 告警。

### 为什么数据新鲜度是业务功能

发射时间可能临时调整。用户看到一条数据时，不仅关心内容，还关心它是什么时候从哪个源更新的。因此 source、sourceUrl、lastSyncedAt 和 freshness 不是运维附属字段，而是产品可信度的一部分。

### 当前降级方案的限制

缓存是单进程 Map，重启即丢失，也无法跨 Serverless 实例共享。生产方案应使用 Redis 保存最后一次成功快照，并加入版本、TTL、命中率和缓存穿透监控。

## 16. 最值得讲的三个技术难点

### 难点一：多源数据标准化与去重

**问题：** 不同 API 对国家、发射状态、实体 ID、时间和关联对象的表达不同。

**方案：** 建立内部枚举和映射函数；保留 source、sourceUrl、externalId 和 rawStatus；以稳定外部 ID 幂等 upsert；同步时解析并缓存关联实体；关键关系使用数据库外键。

**结果：** 前端只消费统一模型，同步任务可以安全重跑，数据也具备可追溯性。

**反思：** 当前跨源实体合并仍主要依赖外部 ID 和名称，后续应使用 EntityAlias、人工审核队列和字段级证据提升实体解析质量。

### 难点二：发射时间变化与数据可信度

**问题：** 发射计划变化频繁，单纯展示数据库记录会让用户误以为它绝对准确。

**方案：** 保存窗口、原始状态、同步时间和来源；将任务按业务时间窗口重新计算；显示 fresh/stale/unknown；为时间与状态变化预留 ChangeEvent 和通知模型。

**结果：** 用户能看到任务计划，也能判断数据是否新鲜。

**反思：** 真正生产化还需要字段级来源优先级、冲突仲裁和官方来源复核。

### 难点三：数据库不可用时避免首页空白

**问题：** 构建或运行期间远程数据库可能超时，核心发射页面会完全失败。

**方案：** 对概览查询设置超时；成功时保存最后一次结果；失败时返回缓存并标记 sourceStatus；没有缓存时返回结构稳定的 503；前端有 loading、error 和数据离线状态。

**结果：** 故障从“页面崩溃”转化为“可解释的降级”。

**反思：** 内存缓存只适合单实例演示，生产应升级为 Redis 和持久快照。

## 17. 常见面试追问与参考答案

### Q1：为什么用 Next.js，不做 React + 独立后端？

当前团队和项目规模下，Next.js 可以统一页面、API、鉴权、中间件和部署，减少跨仓库契约成本。这个项目以查询型业务为主，Route Handler 足够承载。如果同步任务量、团队规模或实时消息复杂度明显增长，我会把同步 Worker 和公共 API 拆成独立服务，而不是一开始过度微服务化。

### Q2：Server Component 和 Client Component 怎么划分？

需要 `useState`、事件、React Query 或浏览器 API 的组件使用 `'use client'`，例如发射筛选、视图切换和倒计时；布局、静态元数据、服务端鉴权和适合直接查库的页面优先放服务端。目标是把交互边界控制在较小范围，而不是整站客户端渲染。

### Q3：为什么使用 React Query？

发射概览需要一分钟轮询，列表还涉及 query key、loading、error、缓存和筛选后重新请求。React Query 将这些服务端状态统一管理，避免手写 `useEffect + fetch + loading`，也便于设置 staleTime 和 refetch 策略。

### Q4：数据库索引怎么考虑？

索引围绕真实查询条件建立。例如 Launch 的 date、status、agencyId、launchSiteId、missionType、orbitName 和 lastSyncedAt；Company 的 country、type 和 name。索引提高查询速度，但也增加写入和存储成本，所以不应给每个字段盲目加索引。上线后还应通过慢查询和 `EXPLAIN ANALYZE` 调整组合索引。

### Q5：如何避免 N+1 查询？

页面 API 使用 Prisma `include/select` 一次读取关联对象；同步任务则用 memoized Promise 缓存同批次的火箭、机构和发射场解析，避免每条发射重复查相同实体。对于大列表还要限制 Payload 数量和字段选择。

### Q6：同步中一部分数据失败怎么办？

记录 skipped 和错误，不让无效记录破坏整批数据；LL2 遇到限流时保留已经抓取的部分结果；总编排器用 `safe` 隔离各数据域失败；每个任务写入 SyncRun，并对连续失败告警。生产环境还应加入死信队列和失败记录重放。

### Q7：为什么同时有 HTTP 缓存和 React Query 缓存？

HTTP 缓存在服务端/CDN 层减少重复计算和数据库压力；React Query 缓存在浏览器层减少页面内重复请求并管理刷新体验。它们处于不同层，TTL 要根据数据变化频率协调，而不是互相替代。

### Q8：JWT 里放角色会有什么问题？

优点是读取快；问题是管理员角色变更后，旧 token 可能在有效期内保留旧权限。因此关键后台操作仍应查询数据库角色，项目的 `getAdminOrNull` 就这样处理。生产中还应设置合理会话时长或 token version 机制。

### Q9：为什么 API Key 用 SHA-256，不用 bcrypt？

API Key 本身是高熵随机值，不像人类密码容易被字典攻击，因此快速的单向 SHA-256 适合查找校验；密码则需要 bcrypt 这类慢哈希抵抗暴力破解。原始 API Key 只在创建时展示一次。

### Q10：这个项目最大的不足是什么？

当前最大不足不是页面数量，而是生产基础设施还没有闭环：缓存和限流是单实例内存实现，通知只有规则与去重逻辑，API Key 路由未完成鉴权持久化，数据源冲突仲裁也不够成熟。我会优先做 Redis、任务队列、真实通知 Worker、端到端测试和可观测性，而不是继续增加低价值页面。

### Q11：如果数据量增长 100 倍怎么办？

先测量瓶颈，再分层处理：为高频筛选建立组合索引；使用 cursor pagination 替代深 offset；把统计聚合做成物化视图或预计算表；热门概览放 Redis/CDN；同步改为队列和增量任务；历史数据分区；搜索迁移到 PostgreSQL FTS 或 Elasticsearch/OpenSearch。不会一开始就全部引入。

### Q12：如何验证国际化没有漏翻？

对四份字典做 key 集合一致性检查；禁止页面新增硬编码界面文案；关键页面分别以四种 locale 构建和截图；实体名称通过独立映射层处理；日期和数字使用 locale-aware formatter。当前仍可进一步把字典一致性检查加入 CI。

### Q13：为什么选择 PostgreSQL，不选择 MongoDB？

核心数据关系稳定且关联很多，还需要唯一约束、外键、筛选、统计和事务。PostgreSQL 更符合模型。部分结构不稳定的外部原始字段可以保存在 Json 列，但不能因此放弃主要关系结构。

### Q14：你如何保证外部 API 变化不会拖垮系统？

通过独立客户端和映射层隔离外部 schema；保留原始状态和来源；请求有超时、重试和限流；同步结果可观测；前端只依赖内部 API。下一步会增加上游响应契约测试和 schema validation，例如 Zod。

### Q15：你在这个项目中的核心贡献是什么？

请根据真实经历组织为三点，不要照抄不属于你的工作：

> 第一，我把产品从功能堆叠收敛为发射计划与产业链两条主线，重构了导航和页面信息架构。第二，我完成或主导了从外部航天 API 到 Prisma 数据模型、同步任务、内部 API 和前端看板的完整数据链路。第三，我补充了国际化、用户与后台、数据健康、缓存降级和测试，使项目从静态展示向可持续更新的全栈平台演进。
